## Redis 主从同步机制与 Redis Cluster 同步机制详解

#### 一、Redis 主从同步机制

Redis 的主从同步机制主要用于数据的复制和负载均衡。它分为全量同步和增量同步两种模式。

1. **全量同步（Full Resynchronization）**

   - **触发条件**：从节点首次连接主节点，或主从复制中断时间过长导致复制积压缓冲区（Repl Backlog）丢失。
   - **流程**：
     1. 从节点发送 PSYNC 命令请求同步。
     2. 主节点判断需要全量同步，执行 BGSAVE 生成 RDB 快照。
     3. 主节点将 RDB 文件发送给从节点。
     4. 从节点清空旧数据，加载 RDB 文件恢复数据。
     5. 主节点将生成 RDB 期间的新写命令存入 replication buffer，并发送给从节点。
   - **特点**：适用于数据量大的情况，但 RDB 生成和传输可能耗时较长，且主节点在同步期间会占用额外内存。

2. **增量同步（Partial Resynchronization）**

   - **触发条件**：从节点短暂断开后重新连接，且主节点的复制积压缓冲区仍存有断线期间的命令。
   - **流程**：
     1. 从节点发送包含主节点 runid 和自身最后复制命令偏移量的 PSYNC 命令。
     2. 主节点检查偏移量，在 repl_backlog 范围内则发送从该偏移量开始的所有新命令。
     3. 从节点接收并执行这些命令，完成数据同步。
   - **特点**：依赖于 repl_backlog，适合短时间断线恢复，避免全量同步的开销。

#### 二、Redis Cluster 的同步机制

Redis Cluster 通过分片实现数据的分布式存储，每个分片内部仍然采用主从复制，但集群模式下还涉及 Gossip 协议和故障转移。

1. **主从复制**：每个主节点对应 1 个或多个从节点，数据同步方式与普通主从相同。

2. **集群间数据同步（Gossip 协议）**：节点间通过 PING/PONG 消息交换集群状态，如槽分配、节点存活情况等。新节点加入或节点下线时，集群通过 Gossip 协议自动更新拓扑。

3. **故障转移（Failover）**：当主节点宕机时，从节点通过 Raft 选举算法竞选成为新主节点，其他节点更新路由表指向新主节点。

#### 三、同步机制的关键配置

- **repl-backlog-size**：调整复制积压缓冲区大小，影响增量同步的容错时间。
- **client-output-buffer-limit slave**：限制主节点对从节点的输出缓冲区，防止从节点长时间不消费导致主节点内存溢出。
- **min-slaves-to-write**：主节点仅在至少 N 个从节点在线时才接受写入，增强数据安全性。
- **repl-diskless-sync**：无盘同步，主节点直接通过网络发送 RDB，避免磁盘 I/O。

#### 四、常见问题及优化建议

1. **主从同步延迟**

   - **原因**：从节点处理慢、网络延迟、主节点写入压力大。
   - **优化**：增大 repl-backlog-size，使用更快的网络，避免主节点执行耗时命令。

2. **从节点过期 Key 处理**

   - **特点**：从节点不会主动删除过期 Key，而是等待主节点发送 DEL 命令同步删除。但从节点读取时会检查 Key 是否过期（逻辑过期）。

3. **数据一致性保证**

   - **默认**：Redis 是最终一致性（异步复制）。
   - **优化**：使用 WAIT 命令阻塞客户端，直到数据同步到至少 N 个从节点。但会降低吞吐量。

#### 总结

- **全量同步**：适用于初次同步或长时间断线，数据一致性强，但性能影响大。
- **增量同步**：适用于短时间断线且 repl_backlog 可用，数据最终一致，性能影响小。
- **生产建议**：合理设置 repl-backlog-size，监控主从节点复制偏移量的差值，避免同步延迟。在需要强一致的场景谨慎使用 WAIT。
